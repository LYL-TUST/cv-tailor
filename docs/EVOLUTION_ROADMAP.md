# 产品演进路线 —— 本地优先 → 账号同步 → 多人架构（v1 → v1.5 → v2）

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0（2026-09-05） |
| 文档性质 | 演进路线图 + 产品决策备忘 + 面试叙事脚本（与 PRD、PRESENTATION_GUIDE 互补，不重复） |
| 一句话主线 | **「本地优先起步 → 验证后演进账号同步 → 预留多人架构」**：账号不是"做不做"的功能开关，而是数据架构三级台阶上的自然演进 |
| 决策背景 | v1.2 起产品走"默认本地 + 可选登录"，PRD §8 取舍 1 已修订；v1.4 已落地 auth + E2E 加密云同步骨架。本文把散落决策串成可验证、可讲述的主线 |
| 现状基线 | 以**当前真实实现**为准（better-sqlite3：`users` + `vault` 单行 blob；本地键 `resume_versions_v1` / `ats_history_v1` / `interview_history_v1` / `arb_draft_*_v1` 等）。注：`docs/ER_DIAGRAM.md` 为早期 MongoDB 设计稿，与本路线图口径不一致时以此文档 + 代码为准 |

## 1. 为什么需要这条主线

一个"简历工具要不要账号"的问题，常规答案有三个，各有代价：

| 常规答案 | 代价 |
|---|---|
| 不做登录，纯本地 | 换设备/清缓存数据即丢，"数据即用即走"无法服务真实留存；产品叙事停在"玩具" |
| 强制注册墙 | 冷启动被劝退；与"隐私优先、无数据上传"的信任杠杆直接冲突 |
| 直接做成云 SaaS | 需要先重写数据层（localStorage → 服务端），在**需求未验证**前投入最大的架构成本，风险最高 |

我们的答案：**把"账号"放到数据架构的三级台阶上，每一级只解决这一级真实存在的问题，用验证数据决定是否走下一级**。这样每个阶段的取舍都是"当时最优"，而不是"预支未来的复杂度"。

**叙事锚点（一句话背下来）**：
> 我做的不是"又一个简历 SaaS"，而是一个**从隐私优先起步、用数据驱动演进的产品**：v1 无账号把"AI 不替你编造"的信任立住；数据证明跨设备是真实需求后，v1.5 用端到端加密做可选云同步；只有留存与同步数据同时达标，才进入 v2 服务端数据模型。每一步都有明确的验证指标和退出条件。

## 2. 三级演进总览

```
                    ┌─────────────────────────────────────────────┐
                    │  用户数据事实源（Single Source of Truth）演进   │
                    └─────────────────────────────────────────────┘

  v1 本地优先             v1.5 账号 + 云同步             v2 多人架构（预留）
┌────────────────┐   ┌──────────────────────┐   ┌──────────────────────────┐
│ localStorage    │ → │ localStorage 为主     │ → │ 服务端数据模型 + API      │
│ （唯一事实源）   │   │ + 云端=加密快照保险箱  │   │ （本地为缓存 / 或纯云）    │
│ 无账号           │   │ 账号=取回钥匙          │   │ 账号=核心资产            │
└────────────────┘   └──────────────────────┘   └──────────────────────────┘
   已完成，闭环可用         下一步（推荐先做）          触发后再做，现在只留缝
   验证：核心功能使用       验证：云同步使用率           验证：同步率 × 留存
   价值：信任杠杆           价值：跨设备恢复             价值：规模化/分享/协作
   成本：≈0                 成本：≈0（业余 1-2 周）       成本：架构级投入，按月计
```

| 维度 | v1 本地优先（现状） | v1.5 账号 + 云同步 | v2 多人架构 |
|---|---|---|---|
| 用户价值 | 零门槛、零上传焦虑 | 换设备/清缓存能恢复 | 多设备实时、可分享/协作 |
| 数据在哪 | 浏览器 localStorage | 本地为主，云端只存密文快照 | 服务端数据库 |
| 登录的角色 | 无 | 可选：云端格子的钥匙 | 核心身份 |
| 隐私承诺 | 数据不离开浏览器 | 服务器只见密文（E2E） | 需重新定义（明示云端可读，或分级） |
| 关键代码资产 | 全部功能 + 备份/历史/草稿层 | `users`/`vault`/AES-GCM 加密层（已有） | 存储适配层 + 同步 API + 配额 |
| 验证指标 | 漏斗可用、AI 护栏有运行证据 | 云同步使用率、恢复成功率 | 留存、NPS、同步冲突率 |
| 触发下一级的信号 | — | 真实用户出现"跨设备"诉求（见 §4.4） | 同步使用率 ≥ 阈值 × 留存达标（见 §5.1） |

## 3. 阶段 1 · v1 本地优先（已完成）

**形态**：无账号、全功能本地可用；多版本简历 / JD 诊断历史 / 模拟面试记录 / 页面草稿全部落在 localStorage；加密备份文件可导出导入。

**为什么本地优先起步是对的（面试要能讲的三点）**：
1. **信任杠杆**：竞品把隐私当免责声明，我们把"数据不离开浏览器"做成架构事实（本地埋点、无账号、无上传），这是差异化而不是口号。
2. **零注册墙冷启动**：不登录能完整跑通"导入 → 打磨 → 诊断 → 面试 → 导出"全流程，漏斗不被注册劝退。
3. **成本 ≈ 0**：无服务器数据库、无 LLM 配额体系也能跑，单人作品集阶段的最优解。

**留给 v1.5/v2 的"预埋"（有意识做的，不是巧合）**：
- 同一套 AES-GCM 加密层同时服务"本地备份文件"与"云端快照"（`backup.js` 的 `encryptData/decryptData`）；
- `users`（scrypt + JWT + 限流）与 `vault`（服务器只见密文）后端骨架在 v1.4 已就位；
- 存储层全部收敛在少数几个 store 模块（`resumeStore` / `historyStore` / `draftStore`），未来加"适配层"时有清晰的替换点。

## 4. 阶段 2 · v1.5 账号 + 云同步（下一步，推荐）

### 4.1 一句话目标
把"手动单快照备份"升级为**"账号名下的多快照加密保险箱 + 一键上传/恢复"**，让"换设备接着用"真正成立。**不建服务端数据模型，不碰本地优先架构。**

### 4.2 明确不做什么（边界，防止范围蔓延）
- ❌ 不做服务端简历数据模型（简历本体仍在 localStorage）
- ❌ 不做自动实时同步 / 多设备并发合并
- ❌ 不做多人协作 / 分享链接
- ❌ 不做支付 / 配额计费 / 找回密码（登录密码走"邮箱人工协助"而非自助找回——E2E 下服务器无法重置密码，需向用户说清，这本身就是产品诚实的一部分）

### 4.3 设计要点（决策备忘录）
| 问题 | v1.4 现状 | v1.5 演进 | 理由 |
|---|---|---|---|
| 快照数量 | `vault` 单行，last-write-wins，再传覆盖旧的 | `vault` → 快照列表（每行一个密文快照 + `created_at`），保留最近 N 份（如 10），手动/自动 prune | 防"手滑上传覆盖唯一备份"；恢复时可选时间点 |
| 密钥体验 | 账号密码 + 同步密码两套，每次手输 | 本设备记忆派生密钥（存本机私有键），**新设备首次输一次同步密码** | E2E 不允许服务器存密钥；"记住此设备"是行业通行解法（类 1Password） |
| 服务器职责 | 存/取/删单 blob | 纯密文桶：按 user 存/取/列/删快照，**零语义校验**（仅体积上限） | 维持"服务器永不接触明文"承诺不变 |
| 恢复策略 | 全量覆盖式合并 | 恢复 = 下载快照 → 浏览器解密 → 与本地**按时间较新合并**（复用现有 `importAllData` 合并逻辑） | v1.5 不做字段级冲突，靠快照+时间戳显式选择，冲突留给 v2 |

**表结构演进方向（better-sqlite3，示意）**：
```sql
-- v1.5：由单行 vault 演进为多快照（服务端只存密文与元信息）
CREATE TABLE vault_blobs (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id),
  enc_payload TEXT NOT NULL,          -- AES-GCM 密文（JSON 字符串）
  created_at TEXT NOT NULL
);
CREATE INDEX idx_vault_blobs_user ON vault_blobs(user_id, created_at DESC);
-- 说明：enc_payload 内部结构 = { salt, iv, encDataKey?, data }，由前端同步密码派生密钥封装，
-- 服务器对该结构无感知，仅做"密文桶"。具体封装沿用在 v1.4 已实现的 AES-GCM 层。
```

### 4.4 验证指标（达标才考虑 v2；不达标则停在 v1.5 继续积累）
- 云同步使用率：登录用户中 ≥ 30% 在 30 天内执行过 ≥ 1 次上传或恢复（快照置备埋点：`cloud_push` / `cloud_pull` 已有雏形，v1.5 补 `cloud_list` / `cloud_restore` 等）；
- 恢复成功率：恢复动作成功完成率 ≥ 95%（失败集中在"忘记同步密码"，需计入产品认知成本）；
- 跨设备信号：单账号绑定设备数 ≥ 2 的用户占比、以及"清缓存后靠云端恢复"的真实事件数；
- 留存对照：登录用户 7 日回访率 vs 未登录用户（本地埋点只能看后者的近似值，作为对照基线即可）。

### 4.5 成本与风险
- 成本：业余 1-2 周；托管用现有 Render 免费/最廉层，数据库免费层即可；**≈ ¥0**。
- 主要风险是 UX 认知：用户容易以为"登录 = 数据自动在云端"。对策：账户区文案写明"账号解决换设备恢复；你的简历默认只在本地"，恢复路径做成向导式。

## 5. 阶段 3 · v2 多人架构（预留，不是现在做）

### 5.1 触发条件（全部满足再启动）
1. v1.5 云同步使用率连续 3 个月 ≥ 15%～30%（量级随产品阶段调整）；
2. 真实用户出现 v1.5 无法覆盖的诉求：多设备实时编辑、误覆盖恢复、或"换台电脑忘了同步密码"等高频投诉；
3. 留存数据证明账号用户显著优于匿名用户（否则说明"账号+同步"不是用户要的东西，多人架构更没有依据）。

> 触发前只做一件事：**在 v1.5 的埋点里把上述信号测出来**。架构投入永远等数据，不让"我觉得用户需要"成为重写数据层的理由。

### 5.2 终局形态对照（到 v2 决策点再二选一，或组合）
| | 路线 A：隐私优先工具（强 E2E） | 路线 B：云 SaaS（服务端数据） |
|---|---|---|
| 数据模型 | 延续本地为主 + 密文快照；可加"端到端加密的字段级同步" | 简历/历史/草稿迁服务端，前端变薄 |
| 账号 | 云端格子的钥匙（弱账号） | 核心身份（强账号） |
| 月成本量级（千人） | 托管 + 少量存储，¥100-300 | 托管/DB/带宽 + **LLM 成本主导**（¥500-3000+） |
| 工程投入 | 中（同步引擎） | 大（数据层迁移 + 冲突 + 配额 + 合规） |
| 差异化 | 强（市面上几乎无人做到"真·端到端"） | 弱（红海：超级简历、简历酱等 + 各 AI 简历） |
| 主要合规议题 | 轻 | 重（求职数据敏感；服务器在美区涉及中国用户数据出境 → 隐私政策 / 境内部署 → 备案） |

### 5.3 若走路线 B 的迁移路径（现在只需"留缝"）
```
现在（各页面直接读写 localStorage store）：
  ATS.jsx / Editor.jsx / Me.jsx ──▶ resumeStore / historyStore / draftStore ──▶ localStorage

v2 迁移（中间加一层适配，页面代码尽量不动）：
  页面 ──▶ 同款 store API ──▶ StorageAdapter(localStorage)    ← 本地优先/离线
                            └─▶ SyncAdapter(服务端 API)       ← 联网走服务端
  服务端：resumes / ats_records / interview_sessions / blobs 表（user_id 维度）
```
- 关键工程点：① store API 全部异步化并加错误态；② 多设备冲突策略（字段级 last-write + 时间戳，或编辑锁）；③ LLM 成本治理（免费额度/套餐配额/缓存）；④ 用户数据导出与删除（合规与信任）。
- **现在唯一要做的"留缝"动作**：写代码时**不要把 localStorage 调用散落到页面里**（当前已收敛在 3 个 store + 若干 key，保持这个纪律即可），以及不要在 store 之上叠加只认 localStorage 的旁路逻辑。

## 6. 面试叙事脚本

### 6.1 60 秒电梯版
"我做了一个 AI 简历工具，核心立场是 **AI 不替你编造，只做裁剪贴合**——所有生成都带真实性校验。架构上我从 **隐私优先的本地优先** 起步：不设账号墙、数据不离开浏览器，把信任做成产品差异。同时我没把'账号'简单砍掉或硬做，而是把它放在演进线上：**v1 本地闭环 → v1.5 端到端加密的账号云同步 → v2 才考虑服务端多人架构**。每一步有验证指标，用数据决定是否投入下一步。这让我既避免了'玩具级'的本地孤岛，也没在需求未验证前就背上 SaaS 的架构成本。"

### 6.2 2 分钟版（含决策故事，可穿插演示）
1. **开场**：一句话定位 + 现场演示"导入简历 → AI 打磨 → JD 诊断 → 模拟面试"闭环（重点展示 AI 护栏：verifier 独立校验每条建议、真实性核查）。
2. **讲本地优先为什么不是偷懒**：无账号 = 信任杠杆（对比竞品注册墙 + 数据可被训练）；本地埋点说明"数据闭环"也能在无服务端数据下成立。
3. **讲"砍过什么"**（诚实取舍的一贯性）：求职信全链路、独立导出页都被砍——因为它们不在主叙事上；**登录我考虑过砍，但没砍**，因为跨设备恢复是真实需求——只是它不该是 v1 的形态。
4. **讲演进设计**：v1.5 快照保险箱 + "记住此设备"密钥方案；服务器只见密文、密码即钥匙、忘了找不回——如何向用户说清这些 trade-off。
5. **收尾**：v2 触发条件（同步使用率 × 留存）——"我给未来留了缝，但绝不让'我觉得'成为重写架构的理由"。

### 6.3 追问 Q&A（背熟口径，别被问倒）
| 追问 | 应答要点 |
|---|---|
| 为什么不做数据库？ | v1 不需要服务端数据：全功能本地闭环；数据库解决的是"跨设备/多人"，那是 v1.5/v2 的问题。**顺序是刻意的**，不是能力缺失 |
| 登录到底解决什么？ | 只解决一件事：换设备/清缓存后的恢复。不是"数据存云端"，简历默认仍在本地 |
| 服务器真看不到数据吗？ | 密文在浏览器用同步密码派生密钥加密后才上传；服务器只有密文桶，字段结构它无法解读（AES-GCM + scrypt 派生） |
| 忘了同步密码怎么办？ | 和"忘了本地加密备份密码"一样无法找回——**密码即钥匙**。产品在注册与上传两处明确告知；v1.5 加"此设备记住密钥"降低日常摩擦，但新设备必须输一次 |
| 现在为什么不做多人/分享？ | 因为还没有数据证明用户需要；做了就是为"我觉得"买单。先测同步使用率与留存，达标才动服务端模型 |
| 多人化后"隐私优先"还成立吗？ | 要么维持 E2E 走路线 A（强隐私差异化）；要么明示"云端可读"并提供数据导出/删除，把选择权交给用户。这是 v2 的产品决策点，现在不假装有答案 |
| localStorage 被清空怎么办？（与 PRESENTATION_GUIDE 呼应） | 三层防线：本机自动保存草稿/历史 → 加密备份文件（密码即钥匙）→ v1.5 账号云快照。不登录也有前两层 |
| 这套埋点有意义吗？ | 本地埋点不能测留存，是已知取舍；价值在①漏斗与事件设计方法论（换 ANY 上报后端即复用）②为 v1.5 云同步埋点做预演 |

## 7. 里程碑与不做清单

**建议里程碑**：
- **M0（已达成）**：本地优先全闭环 + 草稿持久化 + 备份/历史体系
- **M1（下一里程碑，v1.5）**：vault 多快照 + 账户区文案重构 + "记住此设备" + 云同步埋点补全 → 见 §4
- **M2（候选）**：v2 立项评审（对照 §5.1 触发条件）

**不做清单（防止反噬主线）**：
- 不做求职信/猎头/职位推荐等偏离"简历打磨"的功能（已在 PRD §8 下线）；
- 不在 v1.5 前做服务端简历数据模型；
- 不在 v1.5 引入支付与配额（无用户时做计费 = 自嗨）；
- 不把同步做成"自动实时"（v1.5 快照制已够用，自动同步是 v2 冲突策略成熟后的事）。
